## 什么是 Vanilla

讲框架时经常出现一个词：**vanilla**。

Vanilla 本义是"香草"。软件行业借用了这个词，用来表示"原味的、没有额外包装的版本"——就像香草味冰淇淋是冰淇淋的原味一样。所以 **vanilla 前端**指的是：

> 不依赖 React、Vue 这类框架，只用浏览器原生支持的 HTML、CSS、JavaScript 来构建页面。

这个词的边界不必较真——有人会争论"用了第三方库还算不算 vanilla"，这类争论没有实际意义。把它理解成"**没有使用前端框架的写法**"就够了。

## 数据驱动界面

先看 `PageHeading` 这个组件。它把标题的位置空了出来——喂给它什么字，它就显示什么字。个人主页喂"关于我"，文字实验室页喂"文字实验室"，于是同一个组件在两个页面渲染出了不同的标题。

> **界面长什么样，不写死在组件里，而是照着"喂进去的值"来显示。值变了，显示就变。**

用这个视角再看 `App` 组件：它又何尝不是照着一个"值"决定显示哪一页？只不过这个值的来路不同——不是外部组件喂进来的，而是 App 自己持有的：用户点导航栏里的"个人主页"，这个值就变成 `"home"`；点"文字实验室"，它就变成 `"textlab"`。App 再照着这个值，决定当下渲染哪个页面组件。

界面，就是照着一些"值"在显示——这就是**数据驱动界面**（data-driven UI）。

## 数据与界面分离

### 问题：内容和代码搅在一起

项目建成后不会一成不变，尤其是数据部分——副标题、作品列表这些内容发生变化太正常了，而界面结构的变化频率通常远低于数据。

先看一个现象：假设想把首页那句"关于我"改成别的文案，就得打开 `HomePage` 的组件代码，在一堆标签中间找到那句话、再动手修改。内容和代码搅在一起，这就是数据和界面没有分离的状态。

### 方案：一张纯内容清单

数据和界面分离，就是把网站要显示的文字**集中到一个地方**专门管理：

```javascript
// src/data/site.js
export const home = {
	heroTitle: "关于我",
	heroSubtitle: "项目，创意，灵感，心得，我的作品",
	featuredWork: {
		kicker: "作品",
		title: "文字实验室",
		copy: "拼音和情绪，挖掘中文里的细节",
		linkLabel: "打开作品",
	},
	identity: {
		motto: "已识乾坤大，尤怜草木青",
		learning: "零到全栈",
	},
};

export const textLab = {
	heroTitle: "文字实验室",
	heroSubtitle: "拼音和情绪，挖掘中文里的细节",
};
```

这基本就是一张**纯内容清单**——网站上要显示的字都在这儿。（它和 JSON 很像，区别在于对象最后一个成员的结尾允许带逗号。）

组件那边则**不再写死任何文案**：`HomePage` 只负责到这张表里把 `heroTitle` 取出来显示。至于里面写的是"关于我"还是"About Me"，它不关心。

验证效果最直接：

> 打开 `src/data/site.js`，把 `heroTitle` 改成任何字，保存——页面上的大标题当场变化。而 `HomePage.jsx` 和 `PageHeading.jsx` 一个字都没碰。

这就是**数据和界面分开**：

| | 只管什么 |
| --- | --- |
| **组件** | "怎么显示"——排版、样式、结构 |
| **`site.js`** | "显示什么内容" |

两边各管各的，互不干扰。

### 分离的红利：多语言几乎免费

这么一分，好处立刻显现。想给网站做一个**英文版**怎么办？组件一行都不用碰——只要再备一份英文的内容表（把 `site.js` 里的字都译成英文），让组件根据"当前选的是中文还是英文"去读对应那张表就行。排版、结构、样式全部复用。"做多语言"这种听起来很折腾的事，因为数据和界面早早分了家，一下就变简单了。

顺带一提：现在这张表还是写死在文件里的。将来引入后端 API 之后，这些内容完全可以改成从网络接口实时获取——组件依然不需要任何改动。

## 状态驱动 UI

前面例子里被显示的值有两个共同点：一是**从外面喂进来**——哪怕内容集中进了 `site.js`，也还是由父组件读出来再传给子组件；二是**定死的**——不主动去改 `site.js`，它就不会变。

但有些数据需要在用户操作的过程中**自己变**。这种"会变、且一变显示就跟"的值，在 React 里称为组件的**状态（state）**。

一个最纯粹的状态长这样：

- 它是**组件自己的一部分**——不是外面喂的，是自己持有、自己管理的；
- 它有一个**默认值**（一出生就带着）；
- 组件**显示什么，完全照着这个值**；
- 这个值**允许被修改**，而且**一改，显示当场跟着变**。

一个直观的现象：页面上有个输入框，框下面一行写着"已输入 N 字"。往框里多敲几个字、删几个字——**那行数字当场跟着跳**。

框里"当前的文字"就是一个 state：打字的过程就是在修改这个值，下面的字数照着它计算——值一改，界面立刻变。

值得强调的是，这套机制的实现原理完全可以先不深究。React 内部替你盯着这个值、值一变就自动刷新界面——这是它最核心的引擎。需要认出的只是这个现象：**有的值会变，界面会自动跟着它走。**

其实这个机制早就见过一次：导航栏点击切换页面，靠的就是这样一个 state（"现在在哪一页"）。`App` 能控制何时渲染 HomePage、何时渲染 TextLabPage，靠的也是它。

## 小结

- **vanilla** = 不依赖框架、只用浏览器原生能力的写法；
- **数据驱动界面**：界面照着"值"来显示，值变则显示变；
- **数据与界面分离**：内容集中进独立的数据文件，组件只管"怎么显示"、数据表只管"显示什么"——多语言这类需求因此近乎免费；
- **状态驱动 UI**：state 是组件自己持有的可变值，一变界面就跟——它是 React 响应式更新的核心引擎。
